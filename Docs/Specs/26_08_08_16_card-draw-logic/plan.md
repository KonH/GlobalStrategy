# Plan

## Spec faithful summary

Rework only the organisation-owned country-card pool so a new game begins with an empty hand, the configured and persisted hand cap is 8, and production acquisition uses an explicit `DrawCardsCommand` followed by a `ReceiveCardCommand`. A valid draw creates one savable, ordered offer containing up to three weighted, distinct physical card entities without checking playability or affordability; receiving a valid choice places only that card in the lowest free hand slot and returns the other choices to the deck. Ordinary card play no longer refills the hand, while a successful paid discard automatically creates the same up-to-three offer before its discarded card returns to the deck. Bots use the same two commands outside their daily play throttle and prioritize control-raising choices before deterministic fallbacks. Project the authoritative offer, hand cap, and draw availability for the sibling UI plan, and preserve pending offers across save/load.

## Goal

Replace direct and automatic country-card dealing with a deterministic, command-driven choose-one offer lifecycle that is authoritative in ECS state, safe across organisations and saves, consumable by UI, and used unchanged by bots.

## Approach

Keep the existing country deck entity as the owner of hand capacity and attach a savable `PendingCardDraw` component while an offer is active. Attach a savable `CardDrawChoice` with its stable zero-based choice index to each offered card entity. This composes offer state onto the existing deck/cards, survives the reflection-based save pipeline without persisting runtime entity IDs, and keeps `CardInHand` as the sole hand-membership marker. `DrawCardsCommand` carries only `OrgId`; `ReceiveCardCommand` carries `OrgId` and `ChoiceIndex`, because the owner confirmed that org cards are out of scope and choice index resolves otherwise-ambiguous relation-card entities.

Introduce a pure `CountryCardDrawQuery` shared by offer creation, visual projection, and bot observation so deck lookup, hand count/cap, pending state, eligible-card filters, and `CanStartDraw` cannot drift between consumers. Refactor `DrawCardSystem` into the production offer creator while retaining `ForceDrawCard` as a direct debug cheat. It will accept explicit draw commands plus successful paid-discard results, reject invalid requests before consuming RNG, and sample up to three eligible entities with the existing `DeckCopies` weighted-without-replacement algorithm. Exclude `CardInHand`, `CardDrawChoice`, and `CardDiscard`; because offer creation runs before discard cleanup, a paid-discarded card cannot appear in the offer it triggered. `ForceDrawCard` continues to bypass only the hand cap and must also exclude offered choices. Add a separate `ReceiveCardSystem` that validates a previously active offer, rechecks capacity, adds the selected card to the lowest free slot within `CardHand.HandSize`, then removes the deck/card offer markers as one authoritative operation. Remove the obsolete production `CardDraw`/`CheckHandSizeSystem` refill path rather than maintaining two acquisition mechanisms.

The top-level `GameLogic.Update` remains the only system orchestrator. It will resolve receive commands before creating any new offer, retain normal card-removal behavior, capture `DiscardCardSystem` results, synchronize relation/revenge card entities before candidate sampling, feed explicit draw commands and successful paid discards into offer creation, then clean `CardDiscard`. This ordering prevents guessed same-buffer receive commands from selecting a newly sampled offer, lets dynamic cards participate, makes paid discard trigger the shared offer path, and leaves ordinary played/failed cards vacant. On load, reconcile the savable country `CardHand.HandSize` to the current configured value 8 without changing saved hand slots or pending offers.

Extend `CountryActionsState` with ordered draw-choice entries and authoritative `CanStartDraw`. Project offered cards separately from `Hand` and `Deck`, retain choice index plus the card's primary country context for stable UI correlation, and derive hand capacity from the country deck component. Update state equality and benchmarks so offer/cap/availability changes notify consumers. The sibling UI implementation is not part of this plan.

Move bot acquisition ahead of `Bot`'s once-per-date play gate. Extend bot observation with country hand count/cap, draw availability, and ordered offer choices that reuse existing action classification/playability evaluation. Extend the whitelisted command sink with org-stamped draw/receive methods. Keep selection in the shared acquisition path: choose the lowest-index control-raising card usable in a country with control capacity, then another control-raising card, then a currently playable/affordable card, and finally the lowest choice index. Each acquisition tick emits either draw or receive and returns without also playing a card; normal feature play remains daily-gated and the existing feature classes stay responsible only for playing cards already in hand.
