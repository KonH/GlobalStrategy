# Spec: Stop Friendship / Stop Rivalry Cards

## Feature Intent

As a player, I want to play a "Stop Friendship" or "Stop Rivalry" card that names a specific other country the selected country currently holds that exact relation with, so that I have a direct, player-facing way to undo a diplomatic alignment — the mirror of the "Make Friend"/"Make Rival" cards that create one.

## Acceptance Criteria

Legend: `Precondition => Action => Outcome`, grouped under a shared precondition where one applies to several rows.

- The selected country currently has no Friend relation and no Rival relation with any other country.
  - The deck/draw system evaluates a free hand slot for this country => neither "Stop Friendship" nor "Stop Rivalry" is eligible to be drawn, in either variant, for anyone.
- The selected country currently has at least one Friend relation (e.g. friend with France).
  - Player-org opinion with the country's diplomacy advisor is below 80 => no "Stop Friendship" instance naming France is eligible to be drawn into hand.
  - Opinion is 80 or higher, an instance naming France is drawn, and its 100-gold cost is affordable => the instance is shown as playable, labeled with an informal, target-specific phrase rather than a generic "Stop Friendship" name — e.g. "France is not a friend!".
  - Opinion later drops below 80 while that instance already sits in hand => it is shown unplayable, via the same conditions-gated check every other card already goes through; it is not removed from hand.
- The selected country currently has at least one Rival relation (e.g. rival with Spain) — mirrors the Friend case above.
  - Same opinion-gate (80+), same 100-gold cost, same draw/play/unplayable-on-dropped-opinion behavior, but for a "Stop Rivalry" instance naming Spain instead, labeled with its own informal phrase — e.g. "Spain is not our enemy!".
- The selected country is simultaneously friends with France and rivals with Spain, opinion is 80+ for both.
  - Hand/deck are evaluated => a "Stop Friendship" instance naming France and a separate "Stop Rivalry" instance naming Spain can both exist and both be eligible at the same time — they are independent instances, not one card that covers either case.
- The selected country is friends with both France and Germany at the same time, opinion 80+.
  - Hand/deck are evaluated => two independent "Stop Friendship" instances can exist simultaneously, one naming France and one naming Germany; playing or discarding the France-naming instance never changes the Germany-naming instance's existence or eligibility, and vice versa.
- The selected country has many simultaneous relations of the same kind (e.g. five Friend relations at once).
  - Hand/deck are evaluated => there is no cap on how many distinct same-kind instances can exist — one instance is created per current relation, as many as the relation count, competing for hand slots the same as any other eligible card via the existing unmodified per-slot draw fill.
- A "Stop Friendship" instance naming France is sitting in hand, and before the player plays it the Friend(selected country, France) relation stops existing — cleared by another action, a debug command, or a different card instance (including a sibling "Stop Rivalry" instance, if some other mechanic changed the pair to Rival) acting on that same pair.
  - The player attempts to play that instance => the play is rejected/shown unplayable; it must not clear any other relation and must not silently retarget itself to a different country the selected country is still friends with.
  - This holds even if the selected country still has other, different Friend relations at the time (e.g. still friends with Germany) — the France-naming instance stays dead; only a Germany-naming instance (if one exists) is unaffected and playable on its own terms.
- The player plays a "Stop Friendship" instance naming France while the Friend(selected country, France) relation still holds, the instance is playable, and its 100-gold cost is paid.
  - The play resolves => always succeeds, no roll of any kind; the Friend relation between the selected country and France specifically is cleared back to no-relation; every other relation for the selected country (e.g. still-existing Friend with Germany, or any Rival relation) and every relation between unrelated countries is untouched; the card leaves the hand and a replacement is drawn into the vacated slot as usual.
- The player plays a "Stop Rivalry" instance naming Spain under the mirrored conditions.
  - The play resolves the same way, clearing only the Rival(selected country, Spain) relation.
- The player opens the country's Actions panel with either card type, in any state (deck or hand).
  - Neither card ever shows a cooldown label, and playing one instance never blocks another instance of the same or the other relation-stopping card from being drawn or played — consistent with the project-wide removal of the cooldown mechanic.

## Tech Notes

This feature depends on the not-yet-implemented "Make Friend"/"Make Rival" spec (`Docs/Specs/26_07_24_10_country-relation-cards/spec.md`, currently only on `origin/claude/country-cards-friend-rival-pqa37y`) for the opinion-gate wiring, the marker-entity effect-dispatch pattern, and the `SetCountryRelationEffectParams`/`SetCountryRelationSystem` vocabulary. Everything below assumes that spec's opinion-gate plumbing (`ExpressionContext.Opinion`, `ActionPlayability.Evaluate`/`DrawCardSystem.DrawCountryCards` both resolving `Opinion` via the shared character-query helper before evaluating `def.Conditions`) lands first; this spec only adds what's genuinely new for dynamic per-relation targeting.

- **The core problem — today's card model has no way to represent "this specific card copy targets that specific other country":**
  - Every existing country card is one static row in `Assets/Configs/action_config.json` (`ActionDefinition` in `src/Game.Configs/ActionConfig.cs` lines 9-20: `ActionId`, `NameKey`, `DescKey`, `DeckCopies`, `Conditions`, `Cost`, `EffectIds` — no per-instance parameter field of any kind).
  - `InitSystem.cs` (lines 641-649) turns each `ActionDefinition` into `DeckCopies` identical entities per resolved `TargetRole` character, each carrying only `GameAction { ActionId }` + `OrgContext` + `CountryContext` (`src/Game.Components/Action.cs`, `CardDeck.cs`, `CardInHand.cs`). Multiple entities can already share one `ActionId` (that's what `DeckCopies` does), but they are always interchangeable — none carries data that makes one copy different from another.
  - `DrawCardSystem.DrawCountryCards` (lines 91-142), `ActionPlayability.Evaluate` (`src/Game.Systems/ActionPlayability.cs` lines 8-22), `CheckActionConditionSystem.Update` (`src/Game.Systems/CheckActionConditionSystem.cs` line 34, which calls `ActionPlayability.Evaluate` with only `actionId`/`orgId`/`countryId` — no entity), and `VisualStateConverter.BuildEntry` (`src/Game.Main/VisualStateConverter.cs` lines 608-625) all key strictly off `ActionId` string + `(orgId, countryId)` — never off a specific entity's own data.
  - `ActionCardEntry` (`src/Game.Main/VisualState.cs` lines 247-257: `ActionId`, `SlotIndex`, `IsInHand`, `IsUnplayable`, `UnplayableReason`) has no field for a per-instance target, so the UI cannot today distinguish or label two entities sharing `ActionId = "stop_friendship"`.
  - **Decision: add a new `[Savable]` component `RelationCardTarget { string TargetCountryId; RelationKind Kind; }`** (new file `src/Game.Components/RelationCardTarget.cs`, `RelationKind` from `src/Game.Common/RelationKind.cs`), composed onto a card entity alongside its existing `GameAction`/`OrgContext`/`CountryContext`. This is the minimal new modeling required: the definition id (`"stop_friendship"` / `"stop_rivalry"`) stays static and shared, exactly like every other card; only the *instance* carries the dynamic part, following the same "composition onto the existing entity, not a parallel lookup entity" principle as `.claude/rules/unity/ecs_patterns.md`'s composition guidance.
- **`Assets/Configs/action_config.json`: two new static `ActionDefinition` rows**, `stop_friendship` and `stop_rivalry`, `ownerType: "country"`, `targetRole: "diplomacy_advisor"`, `cost: [{ "resourceId": "gold", "amount": 100.0 }]`, same shape as every existing entry. **`deckCopies: 0` for both — deliberately, not a placeholder.** Unlike every other card, instance count is relation-count-driven, not copy-count-driven, so `InitSystem`'s per-`DeckCopies` static generation loop (lines 641-649) must create zero entities for these two ids at game start; all instances come from the new sync system below instead. `conditions` carries two checks: the existing opinion gate (`{"type":"gte","members":[{"type":"opinion"},{"type":"value","value":80}]}`, note the higher 80 threshold vs. Make Friend/Make Rival's 30) and a new per-instance gate `{"type":"gte","members":[{"type":"relationStillExists"},{"type":"value","value":1}]}` (see below). `effectIds` reference one new effect each.
- **New `relationStillExists` DSL node — genuinely new beyond the sibling spec's `hasSuitableRelationTarget`:** `hasSuitableRelationTarget` (sibling spec) answers "does *any* target exist," a single value shared by every copy of Make Friend/Make Rival. This feature needs the opposite granularity: "does *this exact instance's own* targeted relation still hold" — a per-entity question, not a per-card-type one. Add `RelationStillExists` (double) to `ExpressionContext` (`src/Game.Configs/ExpressionNode.cs`) and `case "relationStillExists": return ctx.RelationStillExists;` in `ExpressionNode.Evaluate`. Every call site that evaluates a card's `Conditions` must now resolve this field **per entity** (reading that entity's own `RelationCardTarget`, if present) rather than once per `(orgId, countryId)` the way `Control`/`Opinion` are computed — this is the one place this feature's evaluation loop shape differs from every existing condition:
  - `DrawCardSystem.DrawCountryCards` (lines 91-113): the `ctx` built once at line 93 must have `RelationStillExists` set per-entity, inside the per-entity loop (lines 103-111), by checking `world.Has<RelationCardTarget>(arch.Entities[i])` and, if present, `1.0` if `CountryRelations.GetRelation(world, countryId, target.TargetCountryId) == target.Kind` else `0.0` (default `1.0`/don't-gate for cards without the component, so existing cards are unaffected).
  - `ActionPlayability.Evaluate` (`src/Game.Systems/ActionPlayability.cs` lines 8-22): **signature must change to accept the entity id** (e.g. `Evaluate(IReadOnlyWorld world, ActionConfig config, int entity, string actionId, string orgId, string? countryId)`) so it can look up `RelationCardTarget` on that specific entity before evaluating `def.Conditions`. This ripples to its one production caller, `CheckActionConditionSystem.Update` (line 34, which already has `entity` in scope from its own loop) and to `src/Game.Bots/BotObservation.cs` line 136 (bot AI's own playability check) plus the existing test call sites in `ActionPlayabilityTests.cs`/`BotObservationTests.cs` — all of which currently call `Evaluate` without an entity and will need updating to pass one (tests can pass a dummy/`-1` entity for non-relation cards, which is a no-op since `RelationCardTarget` won't be present).
  - `VisualStateConverter.BuildEntry` (lines 608-625): currently takes only `(actionId, slotIndex, isInHand, orgControl, usedTotal)`; must additionally take the entity (or resolved `RelationCardTarget?`) from its two call sites (lines 585, 598) so it can set `ctx.RelationStillExists` the same way, both for the unplayable-flagging logic already there (`insufficientControl`/`poolFull` at lines 616-622) and — separately — so the UI layer can read the target country id for labeling (see naming note below).
- **New effect: `ClearCountryRelationEffectParams : ActionEffectDefinition { RelationKind Kind }`** (`src/Game.Configs/EffectConfig.cs`, alongside `SetCountryRelationEffectParams`; register under `effectType: "ClearCountryRelation"` in `ActionEffectDefinitionListConverter`'s switch, lines 33-38). Two effect entries in `effect_config.json`: `clear_friendship_effect` (`Kind: Friend`), `clear_rivalry_effect` (`Kind: Rival`) — `Kind` is static per action (stop_friendship always clears a Friend-kind relation), same as the sibling spec's `SetCountryRelationEffectParams.Kind`. Unlike Make Friend/Make Rival, **no random candidate selection is needed** — the specific pair to clear is already fixed at card-creation time by that instance's own `RelationCardTarget.TargetCountryId`, so this effect is simpler than its `Set` counterpart, not a copy of its "50% proximity / 50% random" pick logic.
  - `CreateActionEffectSystem.Update` (`src/Game.Systems/CreateActionEffectSystem.cs`, extend the `foreach (var effectId in def.EffectIds)` dispatch at lines 37-104): add `else if (effectDef is ClearCountryRelationEffectParams clearParams && !string.IsNullOrEmpty(countryId) && world.Has<RelationCardTarget>(entity))` — read `world.Get<RelationCardTarget>(entity).TargetCountryId` from the played card entity itself (the entity already in scope at line 32's `toProcess` loop) and create a marker entity, e.g. `ClearCountryRelationEffect { EffectId, OrgId, CountryId, TargetCountryId }`, mirroring the `DiscoverCountryEffect` marker creation pattern at lines 40-41.
  - New `src/Game.Systems/ClearCountryRelationSystem.cs` (static `Update(World world)`, no `Random` needed — no roll, no pick), invoked from `GameLogic.cs` alongside the sibling spec's `SetCountryRelationSystem.Update` call (both would sit near the existing `DiscoverCountrySystem.Update` call at `GameLogic.cs` line 204, per the top-level-orchestrator-only rule in `.claude/rules/unity/ecs_patterns.md`). For each marker: call `CountryRelations.RemoveRelation(world, marker.CountryId, marker.TargetCountryId)` (`src/Game.Systems/CountryRelations.cs` lines 22-35 — already exists, already used by the debug "Clear relation" command); destroy the marker afterward. Emit a sibling Game Log event (`RelationClearedApplied { OrgId, CountryId, TargetCountryId, Kind }`) after, following the same separate-sibling-entity convention `DiscoverCountrySystem` uses (per the ordering-note precedent already cited in the sibling spec).
- **New `RelationCardSyncSystem` — the piece with no precedent in either sibling spec, because neither Make Friend/Make Rival nor any existing card ever needed to create or reuse card entities dynamically at runtime (`InitSystem` creates all of today's card entities exactly once, at game start, and none are ever destroyed — `CleanupActionEffectsSystem.cs` line 8's comment: "GameAction is persistent card identity ... not cleaned here").** New `src/Game.Systems/RelationCardSyncSystem.cs`, `static void Update(World world, ActionConfig config)`, invoked from `GameLogic.cs` every tick alongside `DrawCardSystem.Update` (line 207). For every `(orgId, countryId)` pair that has a `CardDeck` (i.e. every participating org × available country, same population `InitSystem` already builds), and for every current relation on that country (`CountryRelations.GetRelationsByCountryId(world, countryId)`, `src/Game.Systems/CountryRelations.cs` lines 54-78, giving `Friends`/`Rivals` lists):
  - If no existing entity already has `GameAction.ActionId` matching (`"stop_friendship"` for a friend / `"stop_rivalry"` for a rival) **and** `RelationCardTarget.TargetCountryId` equal to that other country **and** matching `OrgContext`/`CountryContext`, create one: `GameAction { ActionId }`, `OrgContext { OrgId }`, `CountryContext { CountryId }`, `RelationCardTarget { TargetCountryId, Kind }` — deliberately **not** added to hand (`CardInHand` is only ever added by `DrawCardSystem`/`InitActionFromPlayCardSystem`), matching the sibling spec's "no instant push into hand" convention: the new instance is simply now eligible to be found by `DrawCardSystem.DrawCountryCards`'s normal eligible-entity scan on the next free slot.
  - **If a matching entity already exists (in deck, hand, or discard) whether or not its relation still holds, do not create a duplicate and do not destroy it** — this is the deliberate resolution for what happens if the identical pair's relation is cleared and later re-formed: the same, already-existing entity becomes eligible again via the `relationStillExists` condition re-evaluating to `1.0`, rather than accumulating an ever-growing pool of dead entities for a repeatedly-toggled pair. This preserves the "card entities are never destroyed" invariant `CleanupActionEffectsSystem` already establishes for every other card, instead of introducing the first-ever entity-destruction path for a `GameAction`-bearing entity.
  - This system is what turns "N simultaneous Friend relations" into "N simultaneous independent, distinctly-targeted `stop_friendship` entities" (each with its own `RelationCardTarget`), directly answering the multi-target requirement in the Acceptance Criteria.
  - **`CountryRelationsVersion` gap — implemented as part of this feature:** `Docs/Specs/26_07_23_06_country-relations/spec.md`'s Tech Notes describe a `CountryRelationsVersion` singleton counter for change-gating, but it was never actually implemented (`grep -rn "CountryRelationsVersion" src/` returns nothing) — `VisualStateConverter.UpdateCountryRelations` (lines 627-634) recomputes unconditionally every tick instead of version-gating. This feature is the first consumer that actually needs that change-gating, so it adds it:
    - New `CountryRelationsVersion { int Value }` component (`src/Game.Components/CountryRelationsVersion.cs`) — not `[Savable]` (per the `[Savable]` omission pattern in `.claude/rules/unity/ecs_patterns.md`): it is a monotonic dirty-counter, not authoritative state, so resetting to `0` on load and forcing one harmless full resync is acceptable. `InitSystem.cs` creates a single singleton entity carrying it with `Value = 0`, following the existing `GameTime`-style "singleton entity" pattern.
    - `CountryRelations.SetRelation`/`RemoveRelation` (`src/Game.Systems/CountryRelations.cs` lines 8-35) each increment that singleton's `Value` by 1 whenever they actually add or remove a `CountryRelation` entity (`SetRelation`'s unconditional add; `RemoveRelation`'s only-when-`Matches`-found branch) — found via the same archetype-scan-for-the-one-matching-entity approach `GetRelation`/`Matches` already use in this file (not a passed-in entity id), so every existing call site (debug commands, the sibling spec's `SetCountryRelationSystem`, this feature's `ClearCountryRelationSystem`) needs no change.
    - `RelationCardSyncSystem` adds its own singleton component `RelationCardSyncState { int LastSyncedVersion }` (seeded at `-1` by `InitSystem` to force a full scan on the first tick), compares it to the live `CountryRelationsVersion.Value` each tick, and only runs the relation-scan-and-create work above when they differ, then updates `LastSyncedVersion` to match. This is a performance gate only, not a correctness requirement — the per-instance `relationStillExists` condition still re-evaluates every tick regardless of this system's own cadence.
    - `VisualStateConverter.UpdateCountryRelations` and any other existing consumer are left unchanged (still recompute unconditionally) — wiring the new counter into them is separate follow-up work, out of scope here (see Out of Scope).
- **Dynamic card display name/labeling — needs new plumbing, no existing precedent, format now settled:** `ActionVisualConfig` (`Assets/Scripts/Unity/Common/ActionVisualConfig.cs`) keys card art by `actionId` only, which is unaffected (art stays generic per card type, not per target — no new art needed). But the *text* label needs the target country's name, and `ActionCardEntry` currently has no field to carry it. Add a `TargetCountryId` field to `ActionCardEntry` (`src/Game.Main/VisualState.cs` lines 247-257), populated from `RelationCardTarget.TargetCountryId` wherever `BuildEntry`/the org-level `ActionCardEntry` constructor is called for a `stop_friendship`/`stop_rivalry` entity (empty string for every other card, unaffected). **Settled format: an informal, in-voice exclamation naming the country, not a "CardName — Country" label.** `action.stop_friendship.name` locale value becomes a template with a `{0}` placeholder resolving to `"{0} is not a friend!"` (e.g. "France is not a friend!"); `action.stop_rivalry.name` becomes `"{0} is not our enemy!"` (e.g. "Spain is not our enemy!"). UI resolves the display string client-side via `string.Format(_loc.Get("action.stop_friendship.name"), _loc.Get($"country_name.{TargetCountryId}"))` — the same `string.Format(_loc.Get(key), arg)` pattern already used for `action.country.unplayable.insufficient_control` (`Assets/Scripts/Unity/UI/CountryActionsView.cs` line 70) — substituting the resolved `country_name.*` value (`.claude/rules/unity/localization.md`'s existing namespace, already used for all 163 countries) in for `{0}`. Every other existing card's `NameKey` stays a plain non-templated string (unaffected — `string.Format` substitution only applies when `TargetCountryId` is non-empty).
- Diplomacy advisor opinion gate, `hasSuitableRelationTarget`-style plumbing reuse, cooldown-removal precedent: all inherited unchanged from the sibling Make Friend/Make Rival spec once it lands — no separate work needed here beyond raising the threshold to 80 in this feature's own two `conditions` entries.
- Flavor/description text (`DescKey`, unaffected by the dynamic-name templating above): placeholder, non-binding — `stop_friendship` → *"A pointed dismissal, delivered through official channels — the accord is over, whatever comes next is anyone's guess."*; `stop_rivalry` → *"An olive branch, however grudging — the feud ends here, at least on paper."*

## Out of Scope

- Any UI for the player to manually pick which existing relation an instance targets, or to pick a different target for an already-drawn instance — targets are always assigned automatically, one instance per currently-held relation, per the feature request.
- Retargeting a dead instance (whose named relation was cleared) to a different still-existing relation of the same kind — a dead instance stays dead; only the reuse-on-reformation behavior described in Tech Notes can make the same instance live again, and only for the exact same pair.
- Any new relation kinds beyond the existing `Friend`/`Rival`.
- Changes to the debug relation commands/menu (`DebugSetCountryRelationCommand`, `DebugClearCountryRelationCommand`, the "Selected country" debug menu) — unchanged.
- Any gameplay consequence of a relation being cleared beyond the relation data itself changing (AI behavior, combat, events).
- Any success/failure roll — always succeeds once played, per the confirmed requirements.
- Any cooldown or pacing/throttling mechanic for either card.
- Re-balancing the cost, threshold, or mechanics of Make Friend, Make Rival, Sphere of Pressure, the advisor cards, or Royal Audience.
- Card artwork generation (placeholder art acceptable).
- Wiring the new `CountryRelationsVersion` counter into `VisualStateConverter.UpdateCountryRelations` or any other existing consumer beyond this feature's own `RelationCardSyncSystem` — the counter is implemented as part of this feature (see Tech Notes), but retrofitting it elsewhere is separate follow-up work.
- Any cap on simultaneous same-kind instances — confirmed as intentionally uncapped: one instance per current relation, however many that is, competing for hand slots via the existing unmodified per-slot draw fill (see Acceptance Criteria).
- Opponent AI organizations' strategy for choosing among multiple simultaneously-eligible Stop Friendship/Stop Rivalry instances — confirmed skipped for this feature. `Game.Bots/BotObservation.cs`'s existing `ActionPlayability.Evaluate` call site (line 136) only needs the mechanical parameter update required by the entity-aware signature change (Tech Notes); every instance is treated as interchangeable by bot decision-making, same as any other card today. Bot preference logic for which relation to clear is future work.
