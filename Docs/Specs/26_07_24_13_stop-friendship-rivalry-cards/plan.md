# Plan: Stop Friendship / Stop Rivalry Cards

## Spec

As a player, playing a "Stop Friendship" or "Stop Rivalry" card on a selected country undoes one specific existing Friend or Rival relation that country holds with another named country — the mirror of the (not-yet-built) "Make Friend"/"Make Rival" cards.

Key acceptance criteria (see `spec.md` for full detail):
- No instance of either card is eligible for a country with zero Friend/Rival relations.
- Each instance names one specific other country. It is only eligible (drawable/playable) when: the org's opinion with that country's diplomacy advisor is ≥ 80, its 100-gold cost is affordable, **and** the exact relation it names still holds. Opinion dropping below 80 after the instance is drawn makes it unplayable in hand (not removed).
- Multiple simultaneous instances (same kind, naming different countries; or Friend + Rival at once) are independent — playing/discarding one never affects another's existence or eligibility.
- No cap on simultaneous same-kind instances — one instance per current relation.
- If the specifically-named relation is cleared by any other means before the instance is played, that instance is permanently dead (unplayable, non-retargeting) even if the country still holds other relations of the same kind.
- Playing a valid instance always succeeds (no roll), clears only the one named relation, and the vacated hand slot redraws normally.
- Neither card ever shows a cooldown (project-wide cooldown removal, already fully gone from `src/`).

## Approach

**Sequencing decision (read this before reviewing the steps below).** This spec's own Tech Notes assume the sibling "Make Friend / Make Rival" spec (`Docs/Specs/26_07_24_10_country-relation-cards/spec.md`, currently only on `origin/claude/country-cards-friend-rival-pqa37y`, unimplemented and unmerged) lands first and provides the opinion-gate wiring (`ExpressionContext.Opinion` resolution in `ActionPlayability.Evaluate`/`DrawCardSystem.DrawCountryCards`) that this feature also needs. Verified against the actual current tree (not the sibling spec's own possibly-stale line citations): `ExpressionContext.Opinion` exists as a field (`src/Game.Configs/ExpressionNode.cs:7`) and `case "opinion": return ctx.Opinion;` already exists (line 53-55), but **no call site ever sets it** — `ActionPlayability.Evaluate` (line 13) and `DrawCardSystem.DrawCountryCards` (line 93) both only set `Control`, so `Opinion` is always `0`. This is a real, currently-dead gap, exactly as the sibling spec describes.

Rather than blocking this plan on that sibling PR merging first, **this plan implements the opinion-gate plumbing itself, as its own first step**, re-deriving the same shared groundwork (the `CharacterQuery` extraction, `Opinion` resolution in both evaluators, plus one additional gap this feature's own acceptance criteria expose — see below) so this plan is buildable standalone on top of the current, unmodified codebase. This plan does **not** implement anything specific to Make Friend/Make Rival themselves — no `make_friend`/`make_rival` actions, no `SetCountryRelationEffectParams`, no `hasSuitableRelationTarget` node, no proximity-weighted candidate picker. If the sibling PR merges first in practice, Step 1 below becomes a no-op/rebase; if this PR merges first, the sibling plan's own future "opinion gate" step becomes a no-op instead. Either ordering works because the plumbing is idempotent, narrowly-scoped, and owned by neither feature exclusively — flagging this explicitly per the instruction to surface the sequencing choice for objection.

**Second gap found during research, not called out in either spec's Tech Notes:** `VisualStateConverter.BuildEntry` (`src/Game.Main/VisualStateConverter.cs:608-625`) independently re-evaluates `def.Conditions` for the *UI* unplayable-flag/reason, using an `ExpressionContext` that only ever sets `Control` — never `Opinion`. If this is left unset, any opinion-gated card (including this feature's two cards) would evaluate its opinion condition as `0 >= 80` → always false, showing the card permanently unplayable in the UI regardless of the real opinion value, directly contradicting Acceptance Criterion "Opinion is 80 or higher ... instance is shown as playable." Step 1 below fixes this alongside the other two evaluators.

**Third gap found during research, not called out in either spec's Tech Notes:** the play command path has no way to disambiguate between two simultaneous card entities sharing the same `ActionId`. `PlayCardActionCommand` (`src/Game.Commands/PlayCardActionCommand.cs`) carries only `ActionId`/`OrgId`/`CountryId`; `InitActionFromPlayCardSystem.InitCountryCard` (`src/Game.Systems/InitActionFromPlayCardSystem.cs:38-55`) matches purely on `(orgId, countryId, actionId)` and marks the *first* matching hand entity it iterates to — arbitrary when two hand entities share an `ActionId`. Today this never matters because no two hand entities ever share an `ActionId`; this feature is the first to make that possible (a France-`stop_friendship` instance and a Germany-`stop_friendship` instance can sit in hand together). The click-time UI plumbing already has an unused second parameter for exactly this shape of problem (`CountryActionsView.OnCardClicked`'s `targetCharId` string, always passed as `null` today, never read past `HUDDocument.HandleCountryActionCardClicked`) — this plan repurposes and wires that dead parameter through end-to-end as `TargetCountryId`, rather than adding a parallel new one. This is feature-specific (not shared plumbing), included as its own step.

Everything else in the Tech Notes — `RelationCardTarget`, the `relationStillExists` DSL node, `ClearCountryRelationEffectParams`/`ClearCountryRelationSystem`, `RelationCardSyncSystem`, the `CountryRelationsVersion`/`RelationCardSyncState` change-gating pair, and the dynamic display-name templating — is genuinely new to this feature and has no sibling-spec overlap; it is implemented as described in `spec.md`'s Tech Notes, grounded against the real current source below.
