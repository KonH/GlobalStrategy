# Spec: Country-Targeted Make Friend / Make Rival Cards

## Feature Intent

As a player, I want "Make Friend" and "Make Rival" to each name the specific other country they will affect (e.g. "Make France rival!"), so that playing either card is a deliberate choice of who the selected country's new relation is with, instead of the game silently rolling a random target after I commit gold to the play.

## Acceptance Criteria

Legend: `Precondition => Action => Outcome`, grouped under a shared precondition where one applies to several rows.

- The player opens the country-card hand/deck for any country, at any time.
  - There is no longer a single generic "Make Friend" or "Make Rival" card — instead, for every other available country that country could target, a distinct card instance exists naming that exact country (e.g. a "Make France friend!" instance and a separate "Make Germany friend!" instance), mirroring how "Stop Friendship"/"Stop Rivalry" already name a specific country today. Each is its own hand/deck entry, drawn and displayed independently.
- The selected country already has a Friend or Rival relation with a given other country (e.g. already friends with France).
  - The "Make France friend!" and "Make France rival!" instances for that pair are shown unplayable for the selected country, via the same conditions-gated playability check every other card already goes through — exactly mirroring the existing "no suitable target" gate, just now evaluated per named instance instead of "does any target exist anywhere."
  - The selected country's relation with France later changes (cleared by another card, a debug command, or any other means) so no relation remains => the same "Make France friend!"/"Make France rival!" instances become playable again on their own terms (opinion and affordability permitting) — no new instance is created and none is destroyed.
- A country is selected and evaluated against a "Make `X` friend!"/"Make `X` rival!" instance where `X` **is** the selected country itself.
  - That instance is always shown unplayable for that selection, regardless of opinion or relation state — a country can never target itself. (This closes a gap: the relation-check the cards reuse already treats "no relation with self" as trivially true, so an explicit self-exclusion is required — see Tech Notes.)
- The player-org's opinion with the selected country's diplomacy advisor is below 30 (unchanged threshold).
  - No "Make Friend" or "Make Rival" instance, regardless of which country it names, is eligible to be drawn into that org's country-card hand for that evaluation, or is shown playable if already in hand — identical to today's opinion gate, just now applied per named instance.
- The player plays a "Make France rival!" instance with the selected country having no existing relation with France, opinion at or above 30, and the card's gold cost affordable (cost unchanged from today's `make_rival` cost).
  - The play resolves => a Rival relation is set between the selected country and **France specifically** — never any other country. The play always succeeds; there is no roll of any kind, matching today's behavior. Every other country's relations are untouched. The card leaves the hand and a replacement is drawn into the vacated slot as usual.
- The player plays a "Make Germany friend!" instance under the mirrored conditions.
  - The play resolves the same way, setting a Friend relation between the selected country and Germany specifically, using the unchanged `make_friend` cost/opinion gate.
- The player looks at the card face for any "Make Friend"/"Make Rival" instance, in hand or (via debug tooling) in the deck.
  - Its display name reads as an in-voice command naming the target, e.g. "Make France rival!" / "Make Germany friend!" (exact wording per Tech Notes) — not the old generic "Make Friend"/"Make Rival" title.
- The player-org previously had the "friends relation" feature flag disabled (`enableFriendsRelation`).
  - No "Make Friend" instance of any kind exists for that org, for any target country — identical to today's org-wide gate, just applied to the whole per-target instance set instead of the single generic card. `Make Rival` instances are unaffected by this flag, as today.
- Every other existing requirement for either card — the 30+ opinion threshold, the gold cost (unchanged per-card amount), cooldown behavior, and control-pool/affordability checks — behaves exactly as it does today; none of these are renegotiated by this feature.

## Tech Notes

- **Current behavior being replaced (confirmed by reading `main` directly, not from older specs):** `make_friend`/`make_rival` (`Assets/Configs/action_config.json`) are each a single physical card entity per org today (`InitSystem.CreateCountryActionEntities`, `src/Game.Main/InitSystem.cs:670-684` — `GameAction`+`OrgContext`+`CardOwnerType` only, no `CountryContext`, no target component), playable against whichever country is currently selected (the post-`26_08_06_10_card-deck-rework` "dynamic country context" model). Their `conditions` use `hasCountryRelation` with `relationKind: "none"` / `desiredRelationKind: "friend"|"rival"` (`Assets/Configs/action_config.json:207-234`, `:254-281`), which — since neither card carries a `RelationCardTarget` — evaluates via `CountryRelations.HasSuitableRelationTarget` (`src/Game.Systems/CountryRelations.cs:118-156`): "does at least one unrelated country exist anywhere," with `desiredRelationKind` deserialized/validated (`src/Game.Configs/ExpressionNode.cs:125-136`) but never actually read for filtering. On play, `CreateActionEffectSystem` (`src/Game.Systems/CreateActionEffectSystem.cs:103-106`) creates a `SetCountryRelationEffect{OrgId, CountryId, Kind}` marker with **no target**, and `SetCountryRelationSystem.ResolveRelation` (`src/Game.Systems/SetCountryRelationSystem.cs:30-48`) is what currently injects randomness: it builds the candidate list via `CountryRelations.GetSuitableRelationCandidates`, then a 50/50 coin flip between a proximity-weighted pick (`PickByProximity`, inverse-distance from `ProximityMapData`) and a uniform-random pick. This whole resolution path is being removed for these two actions.

- **Reuse the existing `RelationCardTarget` component and its established `{0}`-templating plumbing (`stop_friendship`/`stop_rivalry`/`declare_war` precedent, `src/Game.Components/RelationCardTarget.cs`) — no new component needed.** Give each `make_friend`/`make_rival` card entity a `RelationCardTarget { TargetCountryId, Kind }` where `Kind` is fixed per action (`Friend` for `make_friend`, `Rival` for `make_rival`, same value the effect already carries via `SetCountryRelationEffectParams.Kind`). Unlike `stop_friendship`/`stop_rivalry`/`declare_war` (which also carry `CountryContext` for their "primary" side because their target set is reactive to which relations currently exist, see `Docs/Specs/26_07_24_13_stop-friendship-rivalry-cards/spec.md`), `make_friend`/`make_rival` instances should carry **only** `RelationCardTarget` and no `CountryContext` — the "primary" side stays fully dynamic (whichever country is currently selected, per the card-deck-rework model already in place for non-relation cards), since eligibility only depends on the live relation state between the selected country and this instance's fixed target, not on any pre-existing relation that needs to be discovered. This is a new "dynamic primary + fixed target" shape, distinct from both prior categories, but it composes cleanly with the existing per-entity `RelationCardTarget` read sites (`CountryActionConditionContext.Build`, `VisualStateConverter`, `CreateActionEffectSystem`, `DrawCardSystem.GetTargetCountryId`, `InitActionFromPlayCardSystem`) — none of which require a `CountryContext` to function; they already treat it as optional (`world.TryGet<CountryContext>` in `DrawCardSystem.FindMatchingDeckCard`).

- **Instance creation — static, at init, not a runtime sync system.** Since the country roster is fixed for the whole session (per `Docs/Specs/26_08_02_13_drop-discovery-concept/spec.md`, discovery/progressive reveal no longer exists — every `IsAvailable` country is a `Country` entity from game start and none are added/removed later), a `RelationCardSyncSystem`-style reactive system is unnecessary complexity here. Instead, extend `InitSystem.CreateCountryActionEntities` (`src/Game.Main/InitSystem.cs:635-686`):
  - Add `def.ActionId == "make_friend" || def.ActionId == "make_rival"` to the existing skip condition at line 671 (so the generic single-entity-per-org branch no longer creates the old undifferentiated card for these two ids).
  - Load `countryConfig` in this method the same way `InitSystem.Run`/`SeedCountryRelations` already do (`context.Country.Load()`, `src/Game.Main/InitSystem.cs:24`), and add a new loop, per participating org, per `IsAvailable` country entry (`countryConfig.Countries`, `CountryEntry.IsAvailable`): for `make_friend` (respecting the existing `enableFriendsRelation` gate, same flag already checked at line 676) and for `make_rival`, create one card entity per target country: `GameAction{ActionId}` + `OrgContext{OrgId}` + `CardOwnerType(Country)` + `RelationCardTarget{TargetCountryId=<that country>, Kind=Friend|Rival}`. No exclusion of "self" is needed at creation time — the self-target case is always unplayable per the condition fix below, for whichever org/country ends up being the one selected.
  - This keeps `make_friend`'s existing `TargetRole`/`availableTargetRoles` gate (diplomacy advisor must exist somewhere, line 678) and cost/`deckCopies` gate (`def.DeckCopies <= 0`, line 671) applying to the whole per-target set exactly as it does today to the single card.

- **Condition evaluation — reuse `hasCountryRelation`/`relationKind: "none"` unchanged, but source the target from `RelationCardTarget` instead of leaving it empty.** No DSL change is needed: `CountryActionConditionContext.Build` (`src/Game.Systems/CountryActionConditionContext.cs:60-69`) already resolves `relationTargetCountryId` from `world.Get<RelationCardTarget>(cardEntity).TargetCountryId` whenever the card entity carries the component, and already calls `CountryRelations.MatchesCondition(world, countryId, relationTargetCountryId, "none")` — which, once `relationTargetCountryId` is non-empty, already resolves to the correct **pairwise** check (`GetRelation(world, countryId, relationTargetCountryId) == null`) instead of the "any country anywhere" fallback. This is exactly the "available for countries which don't have friend/rival relation to that country" requirement from the issue, achieved with zero DSL changes — the only reason it doesn't already work this way is that `make_friend`/`make_rival` have never carried a `RelationCardTarget` until this feature.
  - `desiredRelationKind` on each action's existing `hasCountryRelation` condition node stays as-is (`"friend"`/`"rival"` respectively) — it remains wording-only (`ActionConditionDebug.cs:56,151`) and is not touched by this feature.
  - **Genuine gap to close — self-targeting:** `CountryActionConditionContext.Build`'s relation-value loop (`CountryActionConditionContext.cs:60-69`) must additionally treat `countryId == relationTargetCountryId` as a hard "no" for every `relationKind`, not just delegate to `MatchesCondition` — because `CountryRelations.GetRelation` explicitly special-cases equal ids to always return `null` (`CountryRelations.cs`, self-check), which today makes `relationKind: "none"` trivially true for a self-target that was never reachable before (no existing card could ever have `RelationCardTarget.TargetCountryId == CountryContext.CountryId` on the same entity). Add the guard once in this shared loop (e.g. `bool sameCountry = !string.IsNullOrEmpty(relationTargetCountryId) && countryId == relationTargetCountryId;`, folded into the existing `!string.IsNullOrEmpty(countryId) && ...` condition) so it protects `stop_friendship`/`stop_rivalry`/`declare_war` too, though those can never actually hit it (a relation can never be set between a country and itself, per `CountryRelations.SetRelation`'s own equal-id guard).

- **Effect application — remove the random pick entirely; read the fixed target off the played entity, mirroring `ClearCountryRelationEffectParams`'s existing pattern exactly.**
  - `src/Game.Configs/EffectConfig.cs`: no new type needed structurally, but the marker component gains a target field. Add `TargetCountryId` to `SetCountryRelationEffect` (`src/Game.Components/SetCountryRelationEffect.cs`), matching the shape `ClearCountryRelationEffect` already has (`{ EffectId, OrgId, CountryId, TargetCountryId }` + `Kind`).
  - `CreateActionEffectSystem.cs` (`:103-106`): change the `SetCountryRelationEffectParams` branch to also require `world.Has<RelationCardTarget>(entity)` and populate `TargetCountryId = world.Get<RelationCardTarget>(entity).TargetCountryId` on the marker — the same guard/read `ClearCountryRelationEffectParams`'s branch already uses one line below it.
  - `SetCountryRelationSystem.cs`: delete `ResolveRelation`'s candidate search and `PickByProximity` entirely (`:30-75`). The system becomes a direct set, symmetric with `ClearCountryRelationSystem.Update`: for each marker, `relations.SetRelation(world, marker.CountryId, marker.TargetCountryId, marker.Kind)`, emit the existing `RelationSetApplied` game-log event, destroy the marker. Since no candidate search or coin flip remains, the `Random rng` and `int proximityEntity` parameters are no longer needed — simplify the signature to `Update(World world, CountryRelations relations)` (matching `ClearCountryRelationSystem.Update`'s signature) and update the sole call site in `src/Game.Main/GameLogic.cs:275`.
  - `CountryRelations.GetSuitableRelationCandidates` (`CountryRelations.cs`) becomes unused once `SetCountryRelationSystem` no longer calls it — confirm with a repo-wide grep at implement time and remove it if genuinely dead, rather than leaving an orphaned method behind.
  - Existing `src/Game.Tests/SetCountryRelationSystemTests.cs` (proximity-weighting / random-candidate tests) must be rewritten to cover the new direct-set behavior instead; the existing proximity/coin-flip test cases no longer apply and should be removed, not adapted.

- **Draw weight (`DeckCopies`) — must drop from the old single-entity value to `1` per instance, matching the established relation-targeted-card convention, not a value judgment about play frequency.** `DrawCardSystem.DrawCards`' weighted draw (`src/Game.Systems/DrawCardSystem.cs:44-77`) already treats every candidate entity's own `definition.DeckCopies` as its individual draw weight (no per-entity-count distinction survives the card-deck-rework — the weight is per physical entity). Today `make_friend`/`make_rival` are ONE entity each with `deckCopies: 9`/`15` (`Assets/Configs/action_config.json:205,252`); converting to ~19 separate physical entities each (one per other `IsAvailable` country) while keeping `deckCopies: 9`/`15` would multiply their aggregate deck weight roughly 19x, badly skewing the draw pool. Every other relation-targeted, per-instance card already in the codebase (`stop_friendship`, `stop_rivalry`, `declare_war`) uses `deckCopies: 1`; set `make_friend`/`make_rival` to `deckCopies: 1` too for consistency. This mechanically changes the *number* used, but is required by the architecture change itself, not a play-balance decision — call this out explicitly to the owner as a acknowledged side effect (aggregate draw likelihood shifts from a fixed 9/15 to "however many eligible-target instances exist," roughly ~19 each) rather than silently absorbing it as if unrelated to the ask. Re-tuning the exact resulting frequency, if the owner wants a different aggregate weight than "1 per instance," is Out of Scope for this pass (see Out of Scope).

- **Display — reuse the existing `{0}` templating unchanged; only new locale values are needed.** `CountryActionsView.ComposeFaceData` (`Assets/Scripts/Unity/UI/CountryActionsView.cs:135-144`) and `VisualStateConverter`'s `ActionCardEntry.TargetCountryId` population (`src/Game.Main/VisualStateConverter.cs:656-658`) already key off "does this card entity carry `RelationCardTarget`" generically — no code change needed in either file. Update `Assets/Localization/en.asset` (and a real Russian translation via the `localization` skill, not a placeholder, at implement time):
  - `action.make_friend.name`: `Make Friend` → `Make {0} friend!` (matches the issue's own phrasing style, symmetric with `action.make_rival.name`).
  - `action.make_rival.name`: `Make Rival` → `Make {0} rival!` (the issue's exact example, "Make CountryName rival!").
  - `action.make_friend.desc` / `action.make_rival.desc` stay as their current plain, non-templated text (`Mark new country as friend.` / `Mark new country as rival.`) — only the display **name** needs the target, mirroring `stop_friendship`/`stop_rivalry`'s own desc text staying untemplated.

- **Bot AI:** `Game.Bots/BotObservation.cs`'s existing `ActionPlayability.Evaluate` call site already treats every hand/deck card entity individually and needs no change beyond what's already true for `stop_friendship`/`stop_rivalry`/`declare_war` today — bots will see ~19 separate playable-or-not `make_friend`/`make_rival` instances instead of one, exactly as they already do for the other relation-targeted cards. No new bot preference logic for choosing among several eligible targets is introduced by this feature (see Out of Scope, mirrors the sibling spec's own scoping).

## Out of Scope

- Any UI for the player to manually pick or search among the ~19 target-country instances beyond however the existing hand/deck card list already presents multiple simultaneous cards (e.g. for `stop_friendship`) — no new picker widget, filter, or sort is introduced.
- Renegotiating the opinion threshold (30), gold cost, or cooldown duration for either card — explicitly called out by the issue as staying the same.
- Re-tuning the resulting aggregate draw frequency for `make_friend`/`make_rival` beyond the mechanical `deckCopies: 1`-per-instance change required by the new architecture (see Tech Notes) — if the owner wants the two cards to compete for hand slots at a different overall rate than "1 per eligible target," that is separate follow-up balance work.
- Any new relation kinds beyond the existing `Friend`/`Rival`.
- Any success/failure roll for either card — both continue to always succeed once played, unchanged from today.
- Bot preference logic for choosing among multiple simultaneously-eligible `make_friend`/`make_rival` targets — every instance is treated as interchangeable by bot decision-making, matching the same scoping decision already made for `stop_friendship`/`stop_rivalry`.
- Removing or reworking the generic `hasCountryRelation`/`relationKind: "none"` "any suitable target exists anywhere" fallback path (`CountryRelations.HasSuitableRelationTarget`) itself — it stays available for any other caller that still needs an untargeted existence check; this feature only stops `make_friend`/`make_rival` from being the ones relying on it.
- Changes to the debug relation commands/menu (`DebugSetCountryRelationCommand`, `DebugClearCountryRelationCommand`) — unchanged.
- Card artwork — the existing generic per-`actionId` art (not per-target) is reused unchanged, consistent with `stop_friendship`/`stop_rivalry`.
- Any change to which countries are `IsAvailable` or how the country roster is seeded.

## Ambiguities

None open — the owner's issue description fully specified the target behavior (named-country cards, unchanged requirements, availability keyed on "no existing friend/rival relation to that country"), and every remaining implementation choice above (instance creation strategy, `deckCopies` value, self-target handling, locale wording) was resolved to the option most consistent with the existing, already-shipped `stop_friendship`/`stop_rivalry`/`declare_war` pattern rather than left open.
