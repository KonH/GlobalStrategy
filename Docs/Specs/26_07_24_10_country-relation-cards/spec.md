# Spec: Country Relation Cards

## Feature Intent

As a player, I want to play "Make Friend" and "Make Rival" action cards on a selected country, so that I have a direct, player-facing way to shape that country's diplomatic standing with other countries instead of relations only ever being seeded at game start or changed through debug tooling.

## Acceptance Criteria

Legend: `Precondition => Action => Outcome`, grouped under a shared precondition where one applies to several rows.

- The player selects a country and opens its Actions panel for the first time.
  - The country has no prior action-card history => the hand/deck are built as today => "Make Friend" and "Make Rival" join the existing country-card pool (alongside Sphere of Pressure, advisor cards, and Royal Audience) and are eligible to be dealt or drawn like any other country card, each with 3 deck copies — following the same convention every existing country card already uses (Sphere of Pressure, each advisor card, Royal Audience) — subject to their own eligibility conditions below.
- The player-org's opinion with the selected country's diplomacy advisor is below 30.
  - The deck/draw system evaluates "Make Friend" or "Make Rival" for a free hand slot => neither card is eligible to be drawn into the hand, mirroring how advisor/ruler cards are withheld below their own control thresholds today.
  - Opinion later reaches 30 or higher => the card becomes eligible on the next free-slot draw, exactly like any other threshold-gated card — there is no special "push the card into hand the instant the threshold is crossed" mechanic.
  - A copy of either card is already in hand and opinion is (or drops) below 30 => the card is shown unplayable, via the same conditions check every other card's playability already goes through.
- The player-org's opinion with the selected country's diplomacy advisor is 30 or higher, and the selected country currently has at least one other available country that is neither its friend nor its rival ("a suitable candidate exists").
  - "Make Friend" is in hand and its 50-gold cost is affordable => the card is shown as playable.
  - "Make Rival" is in hand and its 50-gold cost is affordable => the card is shown as playable.
- The selected country currently has no suitable candidate (every other available country is already either its friend or its rival with it), regardless of opinion level.
  - The deck/draw system evaluates "Make Friend" or "Make Rival" for a free hand slot => neither card is eligible to be drawn into the hand.
  - A copy of "Make Friend" or "Make Rival" is already sitting in hand when the last suitable candidate disappears (e.g. because another card or a debug action just consumed it) => the card is shown as unplayable via the same conditions-gated playability check above — no separate greyed-out-with-special-label mechanism is introduced for this case.
- The player plays "Make Friend" with a suitable candidate available, opinion at or above 30, and its 50-gold cost is paid.
  - The play resolves => the system automatically picks one suitable candidate country — half the time via a proximity-weighted pick anchored on the selected country (favoring nearer candidates, the same style of weighting `DiscoverCountrySystem` already uses for country discovery), half the time uniformly at random among all suitable candidates — and calls the existing relation model to set a Friend relation between the selected country and that pick, exactly as if the debug "Set friend" action had been used for that pair; the previous relation state for any other pair is untouched.
  - The play always succeeds — there is no success/failure roll of any kind. The played card simply leaves the hand once resolved, and a new card is drawn into the vacated slot as usual.
- The player plays "Make Rival" with a suitable candidate available, opinion at or above 30, and its 50-gold cost is paid.
  - The play resolves => the same automatic pick-and-set flow applies, setting a Rival relation between the selected country and the pick instead of Friend; always succeeds, no roll, same post-play hand/redraw flow as "Make Friend".
- The player opens the country's Actions panel with either card in hand or in the deck pile, at any time.
  - Neither card ever shows a cooldown label or a "next available in N days/months/years" state, and playing one copy never blocks another copy of the same card, or the other relation card, from being drawn or played — the only gates on either card are the opinion threshold and suitable-candidate checks above.
- (Project-wide consequence of removing the cooldown mechanic entirely, see Tech Notes) The player views any country action card, including Sphere of Pressure, the advisor cards, and Royal Audience.
  - The card was previously blocked by an active cooldown => that gating and its label no longer exist anywhere in the game; a played card's copy is immediately eligible again subject only to its own remaining conditions (e.g. Sphere of Pressure's pool-space condition) — no replacement pacing/throttling mechanic is introduced.

## Tech Notes

- New action definitions in `Assets/Configs/action_config.json`: `make_friend` and `make_rival`, both `ownerType: "country"`, `targetRole: "diplomacy_advisor"`, `deckCopies: 3`, `cost: [{ "resourceId": "gold", "amount": 50.0 }]`, following the same shape every existing entry in this file already uses (see `sphere_of_pressure`/`letter_of_commendation_*`/`royal_audience`). No `cooldownDays` field exists on `ActionDefinition` (confirmed by reading `src/Game.Configs/ActionConfig.cs` — see cooldown-removal note below), so nothing needs to be added or omitted there. Each card's `conditions` array carries two checks (both must pass): `{"type":"gte","members":[{"type":"opinion"},{"type":"value","value":30}]}` and `{"type":"gte","members":[{"type":"hasSuitableRelationTarget"},{"type":"value","value":1}]}` (new node type, see below). Each references a new effect via `effectIds`.
- New effect types in `src/Game.Configs/EffectConfig.cs`: add `SetCountryRelationEffectParams : ActionEffectDefinition` with a `Kind` field (`RelationKind`: `Friend`/`Rival`, from `src/Game.Components/CountryRelation.cs` / `GS.Game.Common`), registered in `ActionEffectDefinitionListConverter`'s switch (alongside `DiscoverCountry`/`ControlChange`/`OpinionModifier`) under an `effectType` string such as `"SetCountryRelation"`. Two effect entries (`make_friend_effect`, `make_rival_effect`) in `effect_config.json`, differing only by `Kind`.
- **Opinion gate wiring (closes a real gap — the DSL's `"opinion"` node exists but is currently dead in both runtime evaluators):**
  - Extract the private `GetTargetCharacterByCountryAndRole(World world, string countryId, string targetRole)` helper currently living inside `src/Game.Systems/CreateActionEffectSystem.cs` (lines 134-147) into a shared `public static` helper (e.g. a new `src/Game.Systems/CharacterQuery.cs` alongside `ResourceQuery.cs`, or a public method added to `CountryRelations.cs`) so both `CreateActionEffectSystem` and the two condition-evaluating call sites below can use it. It is a plain query helper, not a system entry point, so extracting/sharing it does not violate `.claude/rules/unity/ecs_patterns.md`'s no-system-to-system-calls rule.
  - In `src/Game.Systems/ActionPlayability.cs::Evaluate` (currently builds `new ExpressionContext { Control = orgControl }` at line 13 and never sets `.Opinion`) and `src/Game.Systems/DrawCardSystem.cs::DrawCountryCards` (same gap at line 93): both unconditionally resolve the diplomacy advisor's opinion for `(orgId, countryId)` via the shared helper + `ResourceQuery.GetValue(world, targetCharId, $"opinion_{orgId}")` (`src/Game.Systems/ResourceQuery.cs`), defaulting to `0` when no diplomacy-advisor character exists for the country or no opinion resource has been created yet for that org/character pair, and set `ctx.Opinion` before evaluating `def.Conditions` — done for every country-card evaluation unconditionally, exactly mirroring how `Control` is already always precomputed regardless of whether a given card's conditions reference it. `ExpressionNode.Evaluate`'s existing `case "opinion": return ctx.Opinion;` (`src/Game.Configs/ExpressionNode.cs` line 53-55) needs no change — it was already correct, just fed a value of `0` everywhere until now.
- **New `hasSuitableRelationTarget` DSL node** (same pattern as the existing `control`/`opinion` scalar context fields, resolved by the caller before evaluation): add a `HasSuitableRelationTarget` double field to `ExpressionContext` (`src/Game.Configs/ExpressionNode.cs`) and a `case "hasSuitableRelationTarget": return ctx.HasSuitableRelationTarget;` branch in `ExpressionNode.Evaluate`. Both `ActionPlayability.Evaluate` and `DrawCardSystem.DrawCountryCards` compute it (alongside `Control`/`Opinion`) by counting `Country` entities that are `IsAvailable` (`src/Game.Configs/CountryConfig.cs`, `CountryEntry.IsAvailable`), are not `countryId` itself, and for which `CountryRelations.GetRelation(world, countryId, candidateId)` (`src/Game.Systems/CountryRelations.cs`) returns `null`; set the field to `1.0` if at least one such candidate exists, else `0.0`. Candidate pool is **all** `IsAvailable` countries regardless of per-org discovery state — no `DiscoveredCountry` filter, per the "all countries" resolution. This same check, reused via the shared `conditions` array on both cards, is what makes the card ineligible to be both drawn into hand and played once already in hand — no separate mechanism needed, matching how every other conditions-gated card (e.g. control-gated advisor cards) already works.
- Candidate selection and relation application follow the same two-phase, marker-component pattern `DiscoverCountry` uses (per `.claude/rules/unity/ecs_patterns.md`'s no-system-to-system-calls rule), rather than resolving the pick inline in `CreateActionEffectSystem`:
  - `src/Game.Systems/CreateActionEffectSystem.cs`: extend the `foreach (var effectId in def.EffectIds)` dispatch (currently handling `DiscoverCountryEffectParams`/`ControlChangeEffectParams`/`OpinionModifierEffectParams`, lines 37-104) with an `else if (effectDef is SetCountryRelationEffectParams relationParams && !string.IsNullOrEmpty(countryId))` branch that creates a new marker entity carrying `{ EffectId, OrgId, CountryId (the selected/source country), Kind }` — mirroring the existing `DiscoverCountryEffect` marker creation at lines 40-41.
  - New `src/Game.Systems/SetCountryRelationSystem.cs` (static, `Update(World world, Random rng)` signature mirroring `DiscoverCountrySystem.Update`), invoked from the top-level orchestrator (`GameLogic.Update`) alongside the existing `DiscoverCountrySystem.Update` call, not from inside another system. For each marker entity: build the candidate list from all `Country` entities where `IsAvailable` is true, excluding the source country itself and excluding any country for which `CountryRelations.GetRelation(world, sourceCountryId, candidateId)` is non-null; pick one candidate as follows (this is the settled design for "50% proximity-based, 50% random", not a remaining ambiguity): flip a 50/50 coin — heads, do a `DiscoverCountrySystem`-style (`src/Game.Systems/DiscoverCountrySystem.cs` lines 62-93) inverse-distance-weighted pick (`w = 1/distance` via `ProximityMapData.Distances`, with the same `minChance` floor) anchored on the **selected country** (`sourceCountryId`, not an org HQ — the relation being formed is between the selected country and the candidate); tails, pick uniformly at random among all eligible candidates. Then call `CountryRelations.SetRelation(world, sourceCountryId, candidateId, kind)` (`src/Game.Systems/CountryRelations.cs`); destroy the marker entity afterward, matching `DiscoverCountrySystem`'s consumption pattern. `SetRelation` already increments `CountryRelationsVersion` per `Docs/Specs/26_07_23_06_country-relations/spec.md`'s Tech Notes, so `VisualStateConverter` picks up the change without extra wiring here.

  - No success/failure roll of any kind is applied anywhere in this flow — the marker-driven relation set always runs to completion once created.

## Out of Scope

- Any UI to let the player manually choose the target country for either card — selection is always automatic, per the feature request.
- Any new relation kinds beyond the existing `Friend`/`Rival` (per `Docs/Specs/26_07_23_06_country-relations/spec.md`'s Out of Scope).
- Changes to the debug relation commands/menu (`DebugSetCountryRelationCommand`, `DebugClearCountryRelationCommand`, the "Selected country" debug menu) — they continue to exist unchanged alongside these new player-facing cards.
- Any gameplay effect of a relation once set (AI behavior changes, combat bonuses, event triggers tied to friend/rival status) — this feature only adds a player-facing way to set the same relation data the earlier spec already modeled; consuming that data elsewhere is future work.
- Cards targeting a specific chosen country's relation to a third specific country the player selects (e.g. "make Country A and Country B rivals" from a country not currently selected) — these cards always operate on the currently-selected country's own relations only.
- Opponent AI organisations playing these cards.
- Card artwork generation (placeholder art acceptable, consistent with the original country-action-cards spec).
- Any success/failure roll for either card — both always succeed once played, by design.
- Any cooldown or other new pacing/throttling mechanic, for these two cards or for any existing country card — cooldown is being removed project-wide as a straight deletion, and this feature does not introduce a replacement mechanic to re-add pacing.
- Re-balancing the cost, success rate, or deck-copy count of any other existing country card as a side effect of the cooldown-removal cleanup — only the dead cooldown display/config artifacts are touched; every other existing card's cost/rate/copies stay exactly as configured today.
