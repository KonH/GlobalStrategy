# Spec: Org Destroyed Window (UI)

## Feature Intent

As a player, I want a clearly notified, flavorful window when an org loses its last foothold and is destroyed, framed as the other orgs' conspiracies finally making it vanish, so that I understand this significant world event happened, using the same visual approach as the existing country-destroy notification (with placeholder art to be replaced later); and when it is my own org that is destroyed and the session ends immediately as a loss (per the Part-A logic spec), I want `EndGameWindow` to appear right after I acknowledge the destroy notification, not stacked on top of it.

**Resolved (owner, 2026-08-11):**
- (5) `OrgDestroyedWindow` is shown for every org destruction, including the player's own — no special-casing, mirroring `CountryDestroyedWindow`.
- (6) When the destroyed org is the player's own, `OrgInfoDocument` (the always-shown panel bound to `VisualState.PlayerOrganization`) hides/grays out — see the new Acceptance Criterion below.
- Additionally, the owner asked that when an org destruction is the trigger for the session ending (`VisualState.GameCompletion.IsCompleted` flips `true` in the same tick), `EndGameWindow` must appear *after* `OrgDestroyedWindow` is acknowledged, using the project's existing modal-sequencing convention — see "EndGameWindow sequencing" below.

## Acceptance Criteria

- **Given** an org has just been destroyed (per the upstream `IsOrgDestroyed` flag / `OrgDestroyedApplied` event produced by the Part-A domain logic, `26_08_11_09_org-destroy-logic`) **When** the destroy event is observed by the UI layer **Then** an `OrgDestroyedWindow` is shown, following the exact same notification/confirmation window pattern as `CountryDestroyedWindowDocument`/`CountryDestroyedWindowView` (itself following `WarResultWindowDocument`'s FIFO queue: `Enqueue`/`TryPeek`/`AcknowledgeCurrent` on a `VisualState` sub-state, `TryOpenIfQueued()`/`OpenCurrent()`, `ModalState.Lock(this)` on open).
- **Given** the `OrgDestroyedWindow` is open **Then** it displays: a fictional/flavor header that includes the destroyed org's name (resolved via the existing `organization_name.{OrgId}` locale-key convention, same pattern `WarResultWindowView.GetOrgName` already uses); a placeholder image element; fictional/flavor body text that also includes the destroyed org's name and evokes the idea of the other orgs' conspiracies finally making it vanish; a close button; and a confirmation button below the body/image — same layout as `CountryDestroyedWindow.uxml`.
- **Given** the country-destroy precedent already has a placeholder image at `Assets/Textures/Events/country_destroy.png` and no org-specific art exists yet **When** this window is implemented **Then** it reuses `Assets/Textures/Events/country_destroy.png` as-is for the placeholder image (per the issue's explicit "same layout and same art for now, I will replace art later" instruction) — no new image asset is generated as part of this feature.
- **Given** the `OrgDestroyedWindow` is open **When** the player presses the close button **Then** the window hides itself, calls `ModalState.Unlock(this)`, and calls `AcknowledgeCurrent()` to pop the queue so the next queued notification (if any) can display — mirroring `CountryDestroyedWindowDocument.Hide()`.
- **Given** the `OrgDestroyedWindow` is open **When** the player presses the confirmation button **Then** it behaves the same as the close button (hide + unlock + acknowledge), since it is the sole action available.
- **Given** the `OrgDestroyedWindow` is open **Then** it blocks all UI for its duration via `ModalState.IsLocked()`, consistent with `CountryDestroyedWindow`'s full modal blocking (not map-only).
- **Given** the `OrgDestroyedWindow` has already been shown and acknowledged for a given destroyed org **When** any other game system or UI flow re-evaluates that org's state afterward **Then** the window is not shown again for that same destruction event — the queue only enqueues once per destroy event, matching `CountryDestroyedResultsState`'s one-shot pattern.
- **Given** multiple orgs are destroyed in close succession **When** their destroy events are observed **Then** their notifications queue and display one after another, matching `CountryDestroyedWindow`'s FIFO behavior.
- **Given** all header, body/flavor text, and button labels shown in `OrgDestroyedWindow` **Then** they are sourced from new locale keys added to `Assets/Localization/en.asset`/`ru.asset` (e.g. `org_destroyed.header_format`, `org_destroyed.body_format`, `org_destroyed.confirm`, following the exact naming convention of `country_destroyed.*`), with the destroyed org's name interpolated via `{0}` into the header and body strings — not hardcoded, with a real Russian translation (not an English placeholder) per the project's localization convention.
- **Given** the `OrgDestroyedWindow` UI implementation **Then** it follows the existing modal window structure used by `CountryDestroyedWindow`: UXML/USS under `Assets/UI/Modal/OrgDestroyedWindow/`, a `OrgDestroyedWindowDocument.cs` MonoBehaviour under `Assets/Scripts/Unity/UI/` (with a paired `OrgDestroyedWindowView.cs`), using VContainer DI for injected services (`VisualState`, `ILocalization`, `ModalState`, `IWriteOnlyCommandAccessor`), registered in `GameLifetimeScope` via `RegisterComponentInHierarchy<OrgDestroyedWindowDocument>()` alongside the other modal window documents, with a `sortingOrder` placed consistently among the existing modal stack (`WarResultWindow` = 510, `CountryDestroyedWindow` = 515).

### Player org panel

- **Given** the destroyed org is the player's own (`OrganizationId == VisualState.PlayerOrganization.OrganizationId`) **When** `OrgInfoDocument` next refreshes **Then** it hides or grays out (implementation-detail choice made during `/plan`/`/implement`; either is acceptable as long as it visually reflects the org no longer being a functioning participant) — resolved (owner, 2026-08-11) in place of "no special handling needed". Destroyed orgs that are *not* the player's own require no `OrgInfoDocument` change, since that panel is only ever bound to the player's own org.

### EndGameWindow sequencing

- **Given** `EndGameWindowDocument` today opens unconditionally and immediately whenever `VisualState.GameCompletion.IsCompleted` becomes `true` (`EndGameWindowDocument.HandleStateChanged`, `Assets/Scripts/Unity/UI/EndGameWindowDocument.cs`) — it never checks `ModalState.IsLocked()` and never subscribes to `ModalState.Unlocked`, unlike `WarResultWindowDocument`/`CountryDestroyedWindowDocument`'s `TryOpenIfQueued()` convention — **When** an org destruction (Part-A) is what flips `GameCompletion.IsCompleted` to `true` in the same tick that also enqueues an `OrgDestroyedWindow` notification for that same destruction **Then** today's behavior would stack `EndGameWindow` (sortingOrder 1100) visually on top of the still-open `OrgDestroyedWindow`, permanently leaving the destroy window's `ModalState` lock un-acknowledged; this feature fixes that by making `EndGameWindowDocument` follow the same "wait your turn" convention already used by the FIFO windows: gate opening on `!_modalState.IsLocked()`, and subscribe to `_modalState.Unlocked` (re-invoking its open-check) in addition to reacting to `GameCompletion` changing — no new `VisualState` queue is introduced, since `GameCompletion.IsCompleted` is itself already a one-shot "pending" signal equivalent to a single-item queue.
- **Given** `EndGameWindow` is now gated behind `ModalState.IsLocked()` **When** the player's own org destruction ends the session (`GameCompletion.IsCompleted` becomes `true` alongside the `OrgDestroyedWindow` enqueue, per Part-A) **Then** `OrgDestroyedWindow` opens first (it acquires the `ModalState` lock via its own existing `TryOpenIfQueued()` path), and `EndGameWindow` opens automatically the moment the player closes/confirms `OrgDestroyedWindow` (`Hide()` → `ModalState.Unlock` → `Unlocked` event → `EndGameWindowDocument`'s handler re-checks and opens) — using the project's existing per-window-type queue + shared `ModalState.Unlocked` convention (`Docs/Specs/26_08_07_08_country-destroy-ui/plan.md`'s "modal coexistence" precedent), not a new shared cross-window-type FIFO.
- **Given** `GameCompletion.IsCompleted` becomes `true` for any other reason (a normal win condition, unrelated to org destruction, with no `OrgDestroyedWindow`/`CountryDestroyedWindow`/`WarResultWindow` notification pending) **When** `EndGameWindowDocument` re-checks after this fix **Then** it opens immediately, exactly as it does today, since `ModalState.IsLocked()` is `false` in that case — this fix only changes timing when another notification window is genuinely queued/open, not the common case.

## Out of Scope

- The underlying domain/ECS logic that determines an org is destroyed (`IsOrgDestroyed` flag, `OrgDestroyedApplied` event, control/hand conditions, win-condition changes, `OrganizationGameOutcome.Result` updates, and the "player org destroyed ⇒ immediate loss" completion path) — covered by the separate Part-A spec (`26_08_11_09_org-destroy-logic`) and treated here only as an already-existing upstream trigger/precondition; this spec only changes how `EndGameWindow` sequences relative to `OrgDestroyedWindow` once that signal fires.
- Producing final flavor/header copy text beyond the "other orgs' conspiracies made it vanish" direction, or generating a new placeholder image asset — the existing `country_destroy.png` is reused as-is per the Resolved criterion above; exact final English/Russian copy is authored during implementation.
- Any change to `EndGameWindow`'s own visual content, layout, or the `WarResultWindow`/`CountryDestroyedWindow`/`GoalsWindow` windows themselves — only `EndGameWindowDocument`'s open-gating logic changes (per "EndGameWindow sequencing" above), and only to make it participate in the existing modal-sequencing convention.
- Any change to map rendering of a destroyed org's territory or presence — a destroyed org's control is already zeroed by Part-A, so it naturally stops appearing as any country's dominant org; no explicit grey-out/removal work here.

## Ambiguities

None outstanding — items (5) and (6) from the original spec draft were resolved by the owner on 2026-08-11 (see inline "Resolved" notes above and the new "Player org panel"/"EndGameWindow sequencing" criteria).
