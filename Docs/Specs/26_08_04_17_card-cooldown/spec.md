# Spec: Card Cooldown

## Feature Intent

As a player (and as a bot-controlled organisation), I want playing an action card to put every card of that same type on a shared cooldown for my organisation, so that I cannot spam-repeat the same kind of action (e.g. "Declare War") back-to-back regardless of which target it names or whether it's a fresh draw or one already sitting in a hand.

## Acceptance Criteria

Legend: `Precondition => Action => Outcome`, grouped under a shared precondition where one applies to several rows.

- An organisation successfully plays any action card (org-owned or country-owned).
  - The play resolves => that card's type enters a cooldown for the playing organisation, starting immediately when the play succeeds.
  - The cooldown duration is not tuned per card type in this iteration => it uses one configurable global default, initially 7 days, applied to every card type.
- An org's card of a given type (e.g. "Declare war on Spain") is on cooldown for that org.
  - Any other instance of the same type for that org — a different target of the same card (e.g. "Declare war on Portugal"), a copy already sitting in a hand, or a fresh copy that would otherwise be drawn — is treated as unplayable until the cooldown ends; "same type" means the same underlying card kind, not the same target instance.
  - A hand slot frees up while that type is on cooldown => the draw system may still draw a new copy of that type into hand (it becomes visible but shown unplayable with its cooldown indicator), or skip it — see Ambiguities for which behaviour is intended.
  - The org views the card (in hand, greyed out) at any point while it's on cooldown => a radial, semi-transparent progress overlay is shown on the card face indicating how much of the cooldown has elapsed / remains.
  - The cooldown period fully elapses => the card (and every other instance of that type for that org) becomes playable again on the next evaluation, the radial overlay disappears, no manual action is required.
- Two different organisations each have a card of the same type available.
  - One org plays its copy => only that org's cooldown for that type is affected; the other org's copies of the same type are unaffected.
- A bot-controlled organisation is deciding which card to play.
  - The bot's card-selection logic never selects a card whose type is currently on cooldown for its own org — cooldown is enforced through the same shared playability check the player-facing UI and server-side validation already use, not a bot-specific rule.
- A card is attempted to be played (by player command or bot command) while its type is on cooldown for that org.
  - The play is rejected the same way any other failed-gate play attempt is rejected (no cost deducted, no effect applied, the card stays exactly where it was).

## Tech Notes

- **History — cooldown existed once and was deliberately removed; this feature reintroduces it under different semantics.** Commit `3ba012c` ("Add country action cards feature with cooldowns and UI") introduced a per-card-instance cooldown (`ActionCooldown` component on the specific played entity, tied to a specific target like one advisor or one ruler). Commit `3baca5f` ("Remove card cooldowns, gate play on gold affordability, add gold debug cheats") deleted it entirely — `src/Game.Components/ActionCooldown.cs` was removed, `CountryActionSystem.TickCooldowns` was removed, and no `cooldownDays`/`cooldownMonths` field exists anywhere in `src/Game.Configs/ActionConfig.cs` or `Assets/Configs/action_config.json` today (verified: `grep -ri cooldown` across `src/` and `Assets/Configs/action_config.json` returns nothing). This feature is a fresh design, not a revert — it must key cooldown by **(OrgId, ActionId)** rather than per played entity, since the requirement is explicitly "same type" (e.g. `declare_war` naming country A and `declare_war` naming country B share one cooldown), which the old per-entity `ActionCooldown` never expressed.
- **Card "type" = `ActionId`.** Every playable card entity carries `GameAction { string ActionId }` (`src/Game.Components/Action.cs`). Country cards targeting different countries (e.g. `declare_war`, `stop_rivalry`) are separate ECS entities that all share the same `ActionId` — confirmed in `src/Game.Systems/RelationCardSyncSystem.cs`'s `EnsureCardInstance` (one entity per relation, same `actionId`) and in `26_07_29_21_declare-war-card/spec.md`. Keying cooldown by `ActionId` (scoped per org) is therefore exactly "same type = declare-war-to-A = declare-war-to-B" as specified in the issue. `ActionId` values are namespaced by `ownerType` in practice (e.g. `sphere_of_pressure` only exists as `ownerType: "country"`, `discover_country` only as `"org"`), so there's no cross-owner-type collision risk from keying by `ActionId` alone.
- **No cooldown state exists today (no config or component to extend) — new pieces needed:**
  - New global setting: `GameSettings.CardCooldownDays` (double, default `7`) in `src/Game.Configs/GameSettings.cs`, plus the matching key in `Assets/Configs/game_settings.json`, following the existing flat-scalar-setting convention already used for `attackerWarProgressDecayPerMonth`, `peaceGoldPerMonth`, etc. This is the single global default the issue asks for ("configurable... set 7 days for all now") — not a per-`ActionDefinition` field, since the request is explicitly one shared default rather than per-type tuning UI.
  - New `[Savable]` component, e.g. `ActionCooldownState { string OrgId; string ActionId; DateTime EndTime; }`, living on a small dedicated tracking entity per `(OrgId, ActionId)` pair that has actually been played at least once — analogous in shape to `CardDeck { OrgId, CountryId }` (`src/Game.Components/CardDeck.cs`), not attached to the played card entity itself (that would reproduce the old per-instance bug where a different target's entity wouldn't be gated).
  - New pure-query helper, e.g. `ActionCooldownQuery` (`src/Game.Systems/`), exposing `IsOnCooldown(world, orgId, actionId, currentTime)` and `GetRemaining(world, orgId, actionId, currentTime)` — a plain non-system helper like `ControlQuery`/`ResourceQuery`, per `.claude/rules/unity/ecs_patterns.md`.
  - New system, e.g. `ApplyActionCooldownSystem.Update(world, currentTime, GameSettings)`, that scans `ActionSucceeded` + `CardUse` + `GameAction` + `OrgContext` entities (same query shape `CreateActionEffectSystem.Update`, `src/Game.Systems/CreateActionEffectSystem.cs`, already uses) and creates/updates the `(OrgId, ActionId)` tracking entity's `EndTime = currentTime.AddDays(settings.CardCooldownDays)`. Slots into `src/Game.Main/GameLogic.cs`'s `Update` right after `ActionSucceededSystem.Update(_world, _actionConfig);` (currently line 249) and before `CreateActionEffectSystem.Update(...)` — both read the same `ActionSucceeded`/`CardUse` marker set that `CleanupActionEffectsSystem.Update` (called at the top of the *next* tick, line 235) sweeps away, matching the existing one-tick marker lifetime every other post-play system already relies on.
- **Play-gating hook — extend the one shared function every consumer already calls, rather than adding a parallel check:**
  - `ActionPlayability.Evaluate(world, config, entity, actionId, orgId, countryId, hqCountryByOrgId)` (`src/Game.Systems/ActionPlayability.cs`) is the single shared gate: called by `CheckActionConditionSystem.Update` (`src/Game.Systems/CheckActionConditionSystem.cs`, the actual server-side authority — only entities that pass get `ActionValid`, and only `ActionValid` entities get cost-deducted/effects-applied via `DeductActionCostSystem`/`CreateActionEffectSystem`) and by `BotObservation` (`src/Game.Bots/BotObservation.cs` line ~130, feeding `BotCardView.IsPlayable`, which `BaselineCardPlayFeature.TryPlay` (`src/Game.Bots/BaselineCardPlayFeature.cs`) already filters on via `if (!card.IsPlayable || ...) return false;`).
  - Add a cooldown check inside `ActionPlayability.Evaluate`, alongside its existing `CanAfford` call, e.g. `if (ActionCooldownQuery.IsOnCooldown(world, orgId, actionId, currentTime)) { return false; }`. This requires threading a new `DateTime currentTime` parameter through `ActionPlayability.Evaluate` and its two call sites: `CheckActionConditionSystem.Update` (add a `DateTime currentTime` parameter; `GameLogic.cs` already has `currentTime` in scope at its call site, line 247) and `BotObservation`'s builder (already resolves `currentDate` via its own `ReadCurrentDate(world)` helper, lines ~48-53).
  - Because this is a shared-function change, both the player-facing server-side validation and the bot's `IsPlayable` flag are covered by one edit — satisfying "bots should understand that concept" without any bot-specific heuristic or new `IBotFeature` (the bot carve-out in `Docs/Constitution.md` doesn't apply here since no new bot feature is added, just a shared gate becoming stricter).
- **UI unplayable-reason wiring is NOT unified today — two more call sites need their own cooldown-aware branch:**
  - `VisualStateConverter.BuildEntry` (`src/Game.Main/VisualStateConverter.cs`, used by `UpdateCountryActions` for the Selected Country actions panel) does **not** call `ActionPlayability.Evaluate` — it re-evaluates `def.Conditions` itself and separately special-cases `pool_full`. It needs its own `ActionCooldownQuery.IsOnCooldown(...)` check added to its `isUnplayable`/`unplayableReason` computation (mirroring the existing `poolFull` special-case at lines ~678-685), producing a new reason string (e.g. `"on_cooldown"`) distinct from the existing `insufficient_opinion`/`no_suitable_target`/`relation_no_longer_exists`/etc. set. `ActionCardEntry` (`src/Game.Main/VisualState.cs`) should also expose the remaining cooldown (e.g. a `TimeSpan?`/`double? CooldownRemainingDays`) so the UI can drive the radial fill fraction, not just a boolean.
  - `UpdateOrgActions` (`src/Game.Main/VisualStateConverter.cs`) currently builds bare `ActionCardEntry(actionId, slot, isInHand)` with **no** `IsUnplayable`/reason at all (confirmed in `26_07_30_12_debug-card-availability/spec.md`'s Tech Notes — org cards' only client-side gate today is cost, checked directly in `OrgActionsView.cs`). Org-owned cards (e.g. `discover_country`) are in scope for this feature too (the issue doesn't say "country cards only"), so `UpdateOrgActions` needs the same cooldown-aware `IsUnplayable`/reason/remaining-time wiring newly added for country cards — this is new scope for org-card visual state, not just a cooldown add-on. See Ambiguities.
  - `CountryActionsView.cs` (`Assets/Scripts/Unity/UI/CountryActionsView.cs`, lines ~74-93) already has a `switch` mapping `UnplayableReason` string constants to locale keys (`action.country.unplayable.*`) for the greyed-out label — add an `"on_cooldown"` branch here and a matching `action.country.unplayable.on_cooldown` locale key (English + real Russian translation via the `localization` skill). `OrgActionsView.cs` currently has no equivalent reason-label switch at all (only cost highlighting) — one would need to be added, following the same pattern.
- **Radial semi-transparent progress overlay — no existing radial/circular UI element in the codebase; this is new UI Toolkit ground:**
  - `ActionCardBuilder.cs` (`Assets/Scripts/Unity/UI/ActionCardBuilder.cs`) builds only rectangular card chrome today (header label, `action-card-art` image, description, footer/cost row) plus one non-radial overlay precedent: `BuildWarWinChanceBadge` — a small rectangular percentage `Label` badge layered on top of `action-card-art` via `AddToClassList`. That's the closest existing pattern for "an overlay element added on top of the card art area," but it is not radial.
  - UI Toolkit in this Unity version (per `.claude/rules/unity/uitoolkit.md`) has no native pie/circular-fill control, and no radial-progress shader/material already exists in the project (searched `Assets/Scripts/Unity/UI` and found none). Feasible directions to evaluate at plan time (not designed here):
    1. **Custom shader material** driving a radial wipe, rendered into a `RenderTexture` and assigned via `VisualElement.style.backgroundImage` — most visually correct, but needs a new URP-compatible shader (per Constitution's URP-only rule) and the WebGL preloaded-assets handling already documented in `.claude/rules/unity/webgl.md` (`Shader.Find` returning null unless the material is in Preloaded Assets or referenced by a scene object).
    2. **Two rotating semi-disc `VisualElement`s** (a common UI-Toolkit radial-wipe trick: two overlapping half-circle masks, each independently rotated via USS `rotate`/`transform-origin`, to sweep 0–360°) — avoids a custom shader entirely, built from two plain sprites/USS shapes; more compatible with the project's existing "no custom shaders in UI" footprint but visually approximates rather than exactly replicates a true radial wipe.
    3. **Runtime-regenerated `Texture2D`** with a filled pie slice recomputed on cooldown-fraction change (not per-frame, since it only needs to update once per relevant tick) — simplest code-wise, avoids shaders, but is a CPU-side per-card texture the plan should confirm is cheap enough given the card counts in hand/deck views (max hand size today is `handSize` from `ActionConfig.Defaults`, currently 3 for org / 5 for country — see `Assets/Configs/action_config.json`).
    Whichever approach the plan picks, it renders as a **semi-transparent** overlay directly on the card face (over `action-card-art` and/or the whole card), per the issue's explicit "radial semi-transparent progress bar" wording, and should hide entirely once the cooldown ends (matching the "opacity 0 to hide while keeping layout space" vs "display: none" guidance in `.claude/rules/unity/uitoolkit.md` — likely `display: none` here since the overlay has no reason to reserve layout space when absent).
  - The original country-action-cards spec's cooldown display (`26_06_20_00_country-action-cards/spec.md`, "Cooldown Display" section) used a **text-only** secondary label ("N days" / "N months" / "N years") below the card name — that entire mechanic was removed along with the rest of the old cooldown system. This issue explicitly supersedes it with a radial visual instead of reviving the old text label; a plan may still choose to pair the radial overlay with a short numeric/day-count label for clarity, but the text-only approach alone does not satisfy the issue's ask.
- **Debug availability panel** (`Assets/Scripts/Unity/UI/DebugCardAvailabilityView.cs`, `src/Game.Configs/ActionConditionDebug.cs`, from `26_07_30_12_debug-card-availability`) already lists per-condition pass/fail rows for each hand/deck card. Adding a cooldown row there (green/red + remaining time) would follow the same established pattern, but is not required to satisfy this issue — flagged as optional follow-up, not required scope.
- **Persistence:** `ActionCooldownState` should be `[Savable]` (its `EndTime` is genuine runtime state set at play time, not derivable from config at load — see the `[Savable]` omission rule in `.claude/rules/unity/ecs_patterns.md`, which only exempts components fully recomputable from config).

## Out of Scope

- Per-card-type tuning of cooldown duration (a config UI or per-`ActionDefinition` override) — this iteration ships one global default (7 days) applied uniformly to every card type, per the issue's own framing ("set 7 days for all now").
- Any change to whether an action succeeds or fails on play — the current codebase has no probabilistic roll on cards anymore (`ActionSucceededSystem` treats "passed all gates" as success, "failed any gate" as failure; there is no RNG roll left to interact with cooldown timing).
- Cross-organisation cooldown sharing — cooldown is strictly per `(OrgId, ActionId)`; one org playing a card never affects another org's copies of the same type.
- Reworking or reviving the old per-instance/per-target `ActionCooldown` component design from commit `3ba012c` — this feature's cooldown key is `(OrgId, ActionId)`, not per played entity.
- A shader/material implementation decision for the radial overlay — the concrete rendering approach (shader vs. rotating discs vs. regenerated texture) is a plan-phase decision, not fixed here.
- Debug Card Availability panel changes (surfacing cooldown as a debug condition row) — optional, not required by this issue.
- Any new `IBotFeature` or bot-specific cooldown heuristic — bots inherit the cooldown gate automatically through the existing shared `ActionPlayability.Evaluate`/`BotObservation.IsPlayable` pipeline; no bot code changes beyond what the shared-gate edit already provides.
- Multiplayer/network synchronization of cooldown state (the project has no multiplayer today).

## Ambiguities

- [NEEDS CLARIFICATION: When a card's type goes on cooldown because a sibling instance was just played, should an already-drawn-but-unplayed instance of that same type currently sitting in another hand slot (or another country's hand, for country cards) stay visibly in the hand — shown greyed out with the radial cooldown overlay, as this spec assumes — or should it be discarded/hidden from hand entirely until the cooldown ends, freeing that hand slot for a draw of a different card type in the meantime?]
- [NEEDS CLARIFICATION: While a card type is on cooldown for an org, should the draw system still be allowed to draw a *new* copy of that type into a freed hand slot (where it would immediately show as on-cooldown/unplayable), or should the draw system actively skip cooldown'd types the same way it already skips condition-gated-out types in `DrawCardSystem.DrawCountryCards`, reserving that hand slot for a different, currently-playable card instead?]
- [NEEDS CLARIFICATION: Does cooldown apply to org-owned cards (`ownerType: "org"`, e.g. `discover_country`) as well as country-owned cards, or is the issue's intent scoped to country action cards only? The issue text doesn't restrict it, and this spec assumes both, but `UpdateOrgActions` currently has zero playability/unplayable-reason wiring at all (see Tech Notes), so including org cards is a meaningfully larger scope than country cards alone.]
- [NEEDS CLARIFICATION: Should cooldown start the instant the play command is validated (`ActionSucceeded` this tick, as this spec assumes, matching how cost is already deducted the same tick), or is there any scenario where "played" should mean something later (e.g. after an animation completes client-side)? Given there's no server-side async step in the current pipeline, this spec assumes tick-of-success is correct, but flags it since the issue only says "when card is played."]
- [NEEDS CLARIFICATION: Should the radial overlay be paired with a numeric remaining-time label (days/months, reusing the old "N days"/"N months"/"N years" formatting from the original country-action-cards spec) for accessibility/precision, or should the radial fill alone be considered sufficient per the issue's literal wording?]
